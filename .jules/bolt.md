## 2025-02-18 - Batch DOM Appends with DocumentFragment
**Learning:** Appending hundreds of nodes individually to the DOM inside loops (like generating station lists) forces synchronous reflows on each append, causing a significant layout thrashing bottleneck.
**Action:** When rendering long lists (like `stationsListEl` or `djStationList`), append newly created elements to a `DocumentFragment` first. Append the fragment to the DOM once the loop finishes to limit DOM operations and improve render performance.

## 2025-02-18 - Caching getComputedStyle properties
**Learning:** Calling `getComputedStyle` synchronously inside a high-frequency `requestAnimationFrame` loop (like rendering an audio visualizer or globe points) causes severe style recalculation layout thrashing, which is a major performance bottleneck for smooth animations.
**Action:** Extract the values generated by `getComputedStyle` once during app startup or theme change, cache them in a global state variable, and use these cached values within animation and rendering loops.

## 2025-02-18 - String manipulation in high-frequency rendering loops
**Learning:** Parsing color strings (e.g., hex to RGB) inside a high-frequency animation loop (like `requestAnimationFrame` running 60fps) within a secondary `for` loop (e.g., once for each of the 128 frequency bins in an audio visualizer) results in thousands of redundant string allocations and `parseInt` calls per second.
**Action:** Move expensive string manipulations and parsing logic outside of inner rendering loops, ideally executing them only once per frame (or better yet, only when the value actually changes) to minimize CPU overhead and garbage collection pauses.

## 2025-02-18 - Caching Objects Outside Animation Loops
**Learning:** Frequent object instantiation (e.g., `new Uint8Array`, `createLinearGradient`) inside high-frequency `requestAnimationFrame` loops (60fps) causes excessive memory allocation and triggers frequent garbage collection pauses, leading to visible stuttering.
**Action:** Always cache persistent objects or buffers in closure variables outside the render loop and reuse them. Only reallocate if dimensions (like `fftSize` or canvas size) dynamically change.

## 2025-02-18 - Batching Canvas Operations
**Learning:** Issuing individual `.beginPath()` and `.stroke()` calls for every line segment (e.g., drawing a grid with 50 lines) has massive overhead in the Canvas 2D API.
**Action:** Batch drawing operations by calling `.beginPath()` once, executing all `.moveTo()` and `.lineTo()` commands in a loop, and calling `.stroke()` exactly once at the end.
## 2024-05-15 - Visualizer requestAnimationFrame String Allocation
**Learning:** `requestAnimationFrame` loops generating complex strings like `rgb(r, g, b)` every frame for every visualizer bar can cause severe garbage collection thrashing and stuttering. Since the byte frequency data comes from an array of 0-255 values, precomputing the 256 possible colors limits string allocation entirely.
**Action:** When drawing visualizers based on limited byte arrays (e.g. `Uint8Array(256)`), cache string properties outside the loop indexing by the data value.

## 2025-03-05 - Optimizing Array Includes with Sets
**Learning:** Checking `favorites.includes(id)` on a large array (5000+ items) inside sorting and filtering loops triggers a massive O(N * M) time complexity overhead, consuming measurable CPU time.
**Action:** When a collection is repeatedly checked for inclusion (`includes`), use a `Set` instead of an `Array`. `Set.has(id)` provides O(1) constant-time lookup, drastically reducing the operation time from ~28ms to ~0.1ms for a million operations.
## 2023-10-19 - Hoisting string operations and caching in large filters
**Learning:** In the `app.js` filter functions (e.g., `filterDeckStations`), processing thousands of items led to repetitive `.toLowerCase()` conversions and string concatenations for every item evaluated. This causes input lag and garbage collection thrashing in JavaScript.
**Action:** Always extract invariant string operations (like converting the search terms `genre` and `subgenre` to lowercase) outside of high-frequency loops. Additionally, cache intermediate string computations (like combining and converting `st.genre` and `st.tags` to lowercase) within the loop into variables so they are only computed once per item, even if checked against multiple filters.
